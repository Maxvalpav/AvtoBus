# 💡 Идеи 301–350: Наблюдаемость и тестирование

### 301. OpenTelemetry по умолчанию, ноль конфигурации
`ActivitySource "AvtoBus"` + семантические конвенции messaging OTel; W3C traceparent в конверте; спаны `publish/receive/process` связаны links-ами.

### 302. Метрики по стандарту OTel messaging
`avtobus.consume.duration` (histogram), `avtobus.publish.count`, `avtobus.queue.depth`, `avtobus.consumer.lag`, `avtobus.outbox.pending`, `avtobus.dlq.size` — Prometheus-ready.

### 303. Critical Time метрика (NServiceBus)
`sent → processed` полное время (включая очередь) — главный SLA-показатель; алерт на p99.

### 304. Consumer lag для всех транспортов
Единая метрика отставания: Kafka — offsets, Rabbit — depth+rate, SQL — count; нормировано в «секундах отставания».

### 305. Трейс «судьбы сообщения»
Все ретраи, DLQ-переходы, реплеи — события одного трейса; в Jaeger видна полная биография сообщения (идея 195).

### 306. Экземплярные логи со скоупом
`ILogger` scope: `MessageId`, `CorrelationId`, `MessageType`, `Attempt` — во всех логах хендлера автоматически.

### 307. Дашборд AvtoBus (CAP/BullMQ-style)
`app.MapAvtoBusDashboard("/bus")`: очереди, консьюмеры, DLQ-браузер с реплеем, саги, проекции, outbox, топология-граф. Blazor/статический SPA, авторизация через ASP.NET policy.

### 308. Живой граф топологии
Автоматическая визуализация: сервисы → очереди → подписки; толщина рёбер = трафик; красные — ошибки (данные из OTel + heartbeats).

### 309. Service map через контрольные сообщения
Каждый инстанс шлёт heartbeat в системный топик: версия, хендлеры, транспорты, аптайм → дашборд знает всю карту флота (ServicePulse-идея).

### 310. Проброс метрик в бизнес-термины
`avtobus.saga.sla.violations{saga="OrderSaga"}` — «застрявшие заказы» видит бизнес, а не только SRE.

### 311. Экспорт AsyncAPI живой системы
Дашборд отдаёт AsyncAPI спеку фактически зарегистрированных каналов — документация никогда не врёт (FastStream).

### 312. Семплирование с tail-based приоритетом
Ошибочные и медленные обработки трейсируются всегда; успешные — 1%; настройка через OTel sampler из коробки.

### 313. Baggage-лимиты и защита
Ограничение размера baggage/headers (защита от «раздувания» контекста через 50 хопов), метрика обрезаний.

### 314. Аномалия-детектор частоты событий
Скользящее окно: тип события вырос/упал в N раз против недельного паттерна → событие `TrafficAnomalyDetected` (можно алертить). Простая статистика, не ML.

### 315. Красная кнопка: `avtobus freeze`
Мгновенная приостановка всех консьюмеров флота (через контрольный топик) при инциденте; `unfreeze` — продолжение. Publish продолжает работать (копится в брокере).

### 316. Тест-харнесс: in-memory вся шина (MassTransit ITestHarness)
```csharp
await using var h = AvtoBusTestHarness.Create(s => s.AddConsumer<OrderPlacedHandler>());
await h.Bus.Publish(new OrderPlaced(id));
(await h.Consumed<OrderPlaced>()).Should().ContainSingle();
h.Published.OfType<ReceiptRequested>().Should().ContainSingle();
```

### 317. Виртуальное время в харнессе
`h.AdvanceTime(2.Days())` — таймауты, ретраи с backoff, cron — всё срабатывает мгновенно (TimeProvider повсюду, идея 230).

### 318. Deterministic-режим харнесса
Один поток, фиксированный seed, упорядоченная доставка — флаки-тесты невозможны; специальный режим race-testing наоборот рандомизирует всё.

### 319. Snapshot-тестирование каскадов
`await Verify(h.AllOutgoingOf<PlaceOrder>())` (Verify-библиотека): весь granulate-граф исходящих сообщений фиксируется снапшотом.

### 320. Контрактные тесты подписок
Тест «подписчик понимает все сообщения, которые реально публикуются» — фикстуры от паблишеров (идея 115) прогоняются через десериализатор+хендлер подписчика в CI.

### 321. Интеграционный test-kit с Testcontainers
`AvtoBusIntegrationFixture`: RabbitMQ/Kafka/Postgres контейнеры, миграции, seed — 10 строк до первого end-to-end теста.

### 322. Тест продюсера без брокера: `CapturingTransport`
Все Send/Publish пишутся в списки — юнит-тест контроллера проверяет исходящие без моков IBus.

### 323. Проверка топологии в CI
`avtobus topology verify --against production-export.json` — новая версия не удалит очередь, на которую кто-то подписан.

### 324. Golden-flow регрессионные тесты
Записанный поток сообщений прод-сценария (анонимизированный) реплеится в CI на новой версии: сравнение итоговых проекций/состояний саг.

### 325. Fault-injection харнесса
`h.FailNext<ChargeCard>(times: 2)` — проверка ретраев/компенсаций декларативно; `h.DelayNext<T>(5.Seconds())` — таймауты.

### 326. Свидетельство идемпотентности в PR
CI-джоб: каждый хендлер с `[Idempotent]` прогоняется дубль-тестом (идея 178); бейдж в README.

### 327. Coverage сообщений
Отчёт: какие типы сообщений не покрыты ни одним тестом харнесса — «message coverage» рядом с code coverage.

### 328. Перф-бенчмарки как тесты
`AvtoBus.Benchmarks` (BenchmarkDotNet): регрессия throughput/allocs на PR — гейт «не медленнее 5%».

### 329. Локальный «мини-прод»: `avtobus dev up`
Compose-профиль: брокер + дашборд + Jaeger + сиды; hot-reload хендлеров через `dotnet watch` — полный цикл локально за минуту.

### 330. Replay-отладка в IDE
`avtobus debug replay <messageId>` — скачивает конверт из audit/DLQ, запускает хендлер локально под дебаггером с прод-пейлоадом (redacted).

### 331. Диагностические события .NET (EventSource)
`AvtoBus-Diagnostics` EventSource для dotnet-trace/dotnet-counters — расследование без APM.

### 332. Аудит «кто послал»
`Envelope.Headers["initiator"]`: user id/service account из HttpContext автоматически; поиск в дашборде «все сообщения, инициированные пользователем X».

### 333. Профили нагрузочного теста
`avtobus loadtest --profile spike.yaml` — генератор трафика по сценарию (ramp, spike, soak) против staging, отчёт latency/lag.

### 334. Датчики ресурсов пайплайна
Метрики каждого middleware: время, ошибки — «водопад» обработки в трейсе показывает, что тормозит: десериализация, валидация или БД.

### 335. Логи-семплинг повторяющихся ошибок
Одинаковая ошибка 1000 раз/мин → логируется 1-я, 10-я, 100-я + счётчик (лог-шторм не убивает Elasticsearch).

### 336. SLO-отчёты по типам сообщений
Декларация: `Slo<OrderPlaced>(p99: 500ms, successRate: 99.9%)` → автоматический error budget и burn-rate алерты.

### 337. Крон-«канарейка»
Системное сообщение-канарейка через всю цепочку (publish → broker → consume) каждые 30с; latency канарейки = живой end-to-end healthcheck.

### 338. Диф трафика между версиями
Canary-деплой: сравнение распределений исходов (успех/ретрай/DLQ) старой и новой версии консьюмера; автооткат при деградации.

### 339. Стоимость сообщений (FinOps)
Оценка $/млн сообщений по транспорту (payload size × тарифы облака) — отчёт «во что обходится каждый топик».

### 340. Умные алерты со «свёрткой причин»
DLQ вырос + лаг вырос + брокер недоступен = ОДИН алерт «брокер», а не 50 (корреляция по топологии).

### 341. Экспорт в разные APM без вендор-лока
Чистый OTel: Jaeger/Tempo/AppInsights/Datadog — одинаково; расширенные конвенции задокументированы.

### 342. Просмотр payload с маскированием по ролям
Дашборд: обычный оператор видит `***` в PII-полях (идея 124), офицер безопасности — полное тело; всё аудируется.

### 343. Часовые пояса и календарь в дашборде
Отображение расписаний cron в TZ пользователя, предпросмотр «следующие 10 срабатываний».

### 344. Мобильные пуш-алерты сагам SLA
Webhook-канал алертов (Slack/Telegram/Teams) из коробки: «12 заказов застряли в AwaitingPayment > 2ч».

### 345. Live-tail сообщений
`avtobus tail orders.order-placed --filter 'body.Total>1000'` — как `kubectl logs -f`, но для топика (семпл, не влияет на консьюмеров — отдельная временная подписка).

### 346. Профилирование памяти конвейера в CI
`dotnet-gcdump` snapshot после нагрузочного прогона; автосравнение retained-объектов между версиями — утечки ловятся до прода.

### 347. Хранилище примеров ошибок
Первые N уникальных (по стектрейсу) ошибок сохраняются с полным контекстом; дедуп по хэшу трейса — «Sentry для шины» встроенный.

### 348. UI-режим «объясни этот трейс»
Кнопка в дашборде: текстовый рассказ по трейсу — «Команда X ждала в очереди 4с (это 90% времени), обработка 200мс, породила 3 события» (генерация из span-ов, шаблонная).

### 349. Событийный «чёрный список» на лету
Оператор блокирует тип/паттерн сообщений через дашборд (например, забагованный продюсер спамит) — консьюмеры дропают до фикса, всё журналируется.

### 350. Отчёт о дрейфе конфигурации флота
Heartbeats несут хэш конфигурации шины; реплики одного сервиса с разными конфигами → предупреждение (частая причина «плавающих» багов).
