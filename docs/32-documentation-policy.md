# Политика документации AvtoBus

## Назначение

Документация разделяет желаемую архитектуру, экспериментальные эскизы и проверенную реализацию. Это предотвращает ситуацию, когда красивый Markdown ошибочно принимают за готовый продукт.

## Иерархия источников

При противоречиях применяется следующий порядок:

1. Реальный код в `src/` и проходящие тесты.
2. ADR со статусом `Accepted`.
3. `03-core-api.md` для публичного API.
4. `01-architecture.md` для архитектурных границ.
5. Proposed ADR как решение на review; Accepted ADR имеет приоритет над общей спецификацией в своей узкой области.
6. `docs/code/*` как экспериментальные эскизы.
7. Файлы 500 идей как каталог возможных направлений.

Пока `src/` отсутствует, пункты 3 и 4 являются каноническими, а `FINAL.md` определяет степень готовности.

## Метки зрелости

| Метка | Значение |
|---|---|
| `Idea` | Возможность рассматривается, API не выбран |
| `Design draft` | Предложены архитектура и trade-offs |
| `Specification` | Поведение описано достаточно для реализации |
| `Code sketch` | Есть пример кода, совместная компиляция не подтверждена |
| `Experimental` | Есть код и тесты, API может ломаться |
| `Stable` | Публичный API покрыт compatibility policy |
| `Deprecated` | Есть срок и путь миграции |

## Правила code snippets

- Блок без метки считается псевдокодом.
- `<!-- compile -->` ставится только перед фрагментом, который извлекается и компилируется doc-test-ом.
- Сниппет не должен объявляться «полным», если требует типы из другого файла.
- Для внешней библиотеки указывается пакет и минимальная проверенная версия.
- Для кода надёжности обязательно описываются failure modes и transaction boundary.

## Правила сравнений

- Версия конкурента и дата проверки обязательны.
- Лицензирование описывается только со ссылкой на официальный источник.
- Колонка AvtoBus явно помечается как `current` или `target`.
- Неизмеренные числа обозначаются `TBD`, а не оценкой.
- Benchmark публикуется с raw results, commit SHA, железом, topology и payload.

## Правила совместимости

- .NET 10 и .NET 11 указываются раздельно: stable target и planned target.
- Нельзя заявлять AOT-ready до успешного `dotnet publish -p:PublishAot=true` без trim/AOT warnings.
- Нельзя заявлять exactly-once без точного определения границы: broker, handler effects или end-to-end.
- Нельзя заявлять production-ready без security review, upgrade tests и эксплуатационного опыта.

## Редакционный чеклист PR

- [ ] Статус документа указан.
- [ ] Нет заявлений о готовности без проверки.
- [ ] Термины согласованы с `29-glossary.md`.
- [ ] Новое публичное API согласуется с `03-core-api.md`.
- [ ] Архитектурное решение сопровождается ADR.
- [ ] Ссылки ведут на существующие файлы.
- [ ] Пример failure-aware: cancellation, timeout и duplicate delivery учтены.
- [ ] Числа имеют источник или помечены как target/TBD.
