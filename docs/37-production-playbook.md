# AvtoBus — Продакшн-руководство: Эксплуатация, Инциденты и Disaster Recovery

> **Статус: Specification draft.** Практические сценарии обслуживания, аварийного восстановления и локализации инцидентов для SRE и DevOps.

---

## 1. Мониторинг и Ключевые Алерты (Alerting Rules)

### 1.1 Критические метрики (SLA/SLO)

| Метрика | Описание | Критический порог | Действие |
|---|---|---|---|
| `avtobus.queue.depth` | Глубина очереди в брокере | > 10,000 сообщений (растёт 15 мин) | Автомасштабирование консьюмеров / Проверка зависших БД |
| `avtobus.critical.time` | Время от отправки до завершения | p99 > 5,000 мс | Проверка подсистемы ретраев и downstream API |
| `avtobus.dead.lettered` | Сообщения в DLQ | > 0 | Инспекция DLQ через CLI/Дашборд |
| `avtobus.outbox.pending` | Зависшие записи в Outbox | > 5,000 | Проверка доступности брокера или Outbox Relay |
| `avtobus.circuit.breaker.open` | Состояние Circuit Breaker | State == Open | Проверка доступности внешнего сервиса |

## 2. Сценарии Инцидентов и Пошаговые Инструкции (Playbooks)

### Сценарий A: Шторм ошибок в консьюмере (Poison Message Storm)

**Симптомы:** Растёт `avtobus.dead.lettered`, CPU воркеров 100%, логи забиты одинаковыми exception.

**Пошаговый план:**
1. **Заморозить обработку проблемного топика:**
   ```bash
   avtobus freeze --queue orders-processing
   ```
2. **Инспектировать первое упавшее сообщение:**
   ```bash
   avtobus dlq peek orders-processing.error --count 1 --format json
   ```
3. **Если причина в баге релиза:**
   - Откатить деплой.
   - Возобновить обработку: `avtobus unfreeze --queue orders-processing`.
   - Запустить плавный реплей накопившихся DLQ с ограничением скорости:
     ```bash
     avtobus dlq replay orders-processing.error --rate 20
     ```
4. **Если причина в повреждённых данных конкретного клиента:**
   - Выгрузить битые сообщения в изолированный карантин:
     ```bash
     avtobus dlq quarantine orders-processing.error --filter "tenant_id=bad_corp"
     ```
   - Разблокировать остальные сообщения.

---

### Сценарий B: Отказ Брокера Сообщений (RabbitMQ / Kafka Unavailable)

**Симптомы:** Логи воркеров содержат `BrokerUnreachableException`. `avtobus.outbox.pending` быстро растёт.

**Поведение AvtoBus:**
1. Приложение **не падает** и продолжает принимать HTTP-запросы.
2. Все исходящие сообщения атомарно пишутся в таблицу `avtobus_outbox` локальной БД.
3. Outbox Relay переходит в режим экспоненциального бэкоффа с джиттером.

**Действия SRE:**
1. Восстановить кластер брокера.
2. Как только брокер станет доступен, Outbox Relay автоматически пробудится и начнёт откачку накопившихся сообщений пачками (`BatchSize = 200`).
3. Мониторить падение `avtobus.outbox.pending` до 0.

---

### Сценарий C: Падение Базы Данных в процессе Outbox Relay

**Симптомы:** `OutboxRelay` ловит `DbException`.

**Гарантия безопасности:**
- Очередность сообщений в Outbox защищена монотонным ID (`BIGSERIAL`) и претензией `SKIP LOCKED`.
- Если воркер упал посреди отправки пачки, незавершённые претензии сбрасываются по таймауту (`StaleClaimTimeout = 2m`), и пачку подхватывает любой другой живой воркер.
- **Потери данных нет.** Возможен дубликат отправки, который гасится `Inbox`-дедупликацией на стороне получателя.

## 3. Резервное копирование и Disaster Recovery (DR)

### 3.1 Стратегия восстановления после полной катастрофы дата-центра

1. **База данных (PostgreSQL):** Восстанавливается из WAL-g / PITR бэкапа на момент времени $T$.
2. **Брокер (RabbitMQ / Kafka):**
   - Топология пересоздаётся автоматически при старте воркеров (`bus.CreateTopologyAsync()`).
   - Сообщения в брокере считаются эфемерными; источник истины — БД с Outbox и Event Store.
3. **Восстановление согласованности (Reconciliation):**
   - Выполнить сверку последней обработанной последовательности:
     ```bash
     avtobus doctor reconcile --db-connection "..." --broker "..."
     ```
   - Outbox Relay автоматически переотправит все записи `SentAt IS NULL`.

## 4. Обслуживание в Продакшне (Routine Maintenance)

### 4.1 Очистка Outbox и Inbox (Purge & Vacuum)

По умолчанию фоновый сервис `OutboxCleanup` каждые 15 минут удаляет обработанные записи старше 7 дней.

Для высоконагруженных систем (> 50 млн сообщений/сутки) рекомендуется использовать партиционирование таблиц PostgreSQL по дням:

```sql
-- Автоматическое создание суточных партиций
SELECT create_monthly_partitions('avtobus_outbox');

-- Быстрый DROP старой суточной партиции вместо тяжелого DELETE
DROP TABLE avtobus_outbox_2026_01_01;
```
