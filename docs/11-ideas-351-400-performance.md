# 💡 Идеи 351–400: Производительность и масштабирование

### 351. Zero-reflection: полный codegen горячего пути
Диспетчеры, фабрики, сериализация — Source Generators; в рантайме ни одного `MethodInfo.Invoke`/`Activator.CreateInstance`.

### 352. Native AOT поддержка первого класса
Весь Core + InMemory + RabbitMQ + STJ работают под AOT; CI собирает AOT-sample; старт воркера < 50 мс, RSS < 30 МБ.

### 353. `System.Threading.Channels` как внутренний конвейер
Bounded channels на каждом этапе; back-pressure по построению; никаких ConcurrentQueue+Semaphore самоделок.

### 354. Пулинг конвертов и буферов
`Envelope` тела — из `MemoryPool<byte>`; возврат в пул после ack; метрика pool-misses.

### 355. `IBufferWriter<byte>` сериализация без промежуточных массивов
STJ `Utf8JsonWriter` → прямо в буфер транспорта; на приёме — `ReadOnlySequence<byte>` без склейки.

### 356. ValueTask повсюду на горячем пути
Синхронные завершения (in-memory, кэш-попадания) не аллоцируют Task.

### 357. Обработка батчами на уровне транспорта
Kafka consume batch → один scope, один UoW, один коммит оффсетов на батч (настраиваемо) — 10–50x throughput на записи в БД.

### 358. Конкурентность: `MaxParallelism` + worker-shards
N воркеров на консьюмер; партиционирование по ключу поверх (идея 25) — параллельно, но упорядоченно.

### 359. Prefetch-автотюнинг
Алгоритм: prefetch = rate × p95-latency × 2 (формула из практик RabbitMQ), пересчёт раз в 30с в заданных границах.

### 360. Батч publisher confirms
Ожидание confirm-ов группой (multiple=true), корреляция по deliveryTag-диапазонам — паблиш 100k+/с на одном соединении.

### 361. Пайплайн-компиляция: один делегат вместо цепочки
Middleware-цепочка компилируется генератором в единый метод (инлайн вызовов) — как скомпилированный RequestDelegate ASP.NET Core.

### 362. Отказ от boxing в диспетчеризации
Generic-диспетчеры `IMessageDispatcher<T>`; value-type сообщения (редко, но можно) не боксятся.

### 363. FrozenDictionary для роутинг-таблиц
Таблицы тип→маршрут, строка→диспетчер строятся при старте во `FrozenDictionary` — lookup быстрее обычного словаря.

### 364. Span-парсинг заголовков
Разбор traceparent/типов без Substring: `ReadOnlySpan<char>` и `Utf8Parser`.

### 365. Локальность: sticky partition → CPU
Партиция-канал закрепляется за воркером (и косвенно ядром) — кэш-локальность стейта per-key хендлеров.

### 366. Метрики аллокаций на сообщение как SLA
Бенчмарк-гейт: ≤ 1 КБ аллокаций на publish, ≤ 2 КБ на consume (без пользовательского кода); отчёт в PR.

### 367. Быстрый путь локальной доставки
Подписчик в том же процессе → минуя сериализацию (передача ссылки на immutable record) — опция `AllowInProcessShortcut` (по умолчанию on для InMemory, off для брокеров — сохранение wire-семантики).

### 368. Отложенная материализация scope
DI-scope создаётся только если хендлер реально требует scoped-зависимости (генератор знает) — для тонких хендлеров экономия ~микросекунды и аллокаций.

### 369. Кэш скомпилированных запросов outbox
Подготовленные команды (NpgsqlBatch), COPY для bulk-вставок outbox при батч-паблише.

### 370. Outbox: групповая отметка отправки
`UPDATE outbox SET sent=now() WHERE id = ANY(@ids)` одним запросом на батч; отправка/отметка конвейеризированы.

### 371. Спил на диск при пиках (spill-to-disk)
Переполнение локального буфера → спил в SQLite/файл вместо OOM или блокировки паблишера (настраиваемая стратегия).

### 372. Компрессия словарём Zstd per-topic
Обучение словаря на семплах топика (`avtobus compress train`) — JSON события жмутся в 8–15x, CPU меньше gzip.

### 373. Автоскейл консьюмеров внутри процесса
Контроллер: lag растёт и CPU < 70% → +воркер; lag=0 длительно → −воркер; границы min/max; гистерезис.

### 374. KEDA/HPA рецепты наружного скейла
Метрики лага в формате external metrics; готовые Helm-values; scale-to-zero для редких очередей (активация по глубине).

### 375. Партиционный ребаланс без остановки мира
Kafka cooperative-sticky из коробки; для SQL/Rabbit-эмуляций — плавная передача партиций с drain-ом (без глобальной паузы, как в старом Kafka eager).

### 376. Иерархический шардинг тяжёлых ключей
Горячий ключ (селебрити-аккаунт) детектится по частоте → саб-шардинг key#0..key#7 с агрегационной стадией (идея из стрим-процессинга).

### 377. Read-модели с ETag/If-None-Match
Проекции отдают версию (global_seq); API-кэши и CDN работают бесплатно.

### 378. Nagle-подобная агрегация мелких publish
Окно 1–5 мс собирает мелкие сообщения в батч транспорта (opt-in, для телеметрии/тиков) — 10x throughput ценой миллисекунд латентности.

### 379. Профиль «низкая латентность»
`bus.Profile(LatencyProfile.Low)`: prefetch=1..малый, батчинг off, confirm sync, GC SustainedLowLatency — для трейдинга/игр.

### 380. Профиль «высокая пропускная»
`ThroughputProfile.High`: большие батчи, confirm группами, parallel partitions, Server GC — для аналитики/ETL.

### 381. io_uring/RIO-готовность транспортного слоя
Абстракция сокет-слоя допускает подключение экспериментальных бэкендов; бенч-стенд в репо.

### 382. Многопроцессная обработка (sandboxed processors, BullMQ)
CPU-тяжёлые хендлеры — в дочерних процессах-воркерах с IPC через файловый лог (идея 100): краш нативной либы не роняет консьюмер.

### 383. Инкрементальная десериализация больших коллекций
`IAsyncEnumerable<Item>` поле контракта стримится из JSON-массива — обработка начинается до полного парсинга гигабайтного экспорта (claim-check сценарий).

### 384. Ленивая инициализация редких консьюмеров
Подписка активируется при первом сообщении (subject-hint от брокера), пустые консьюмеры не жгут соединения — для сервисов с сотнями топиков.

### 385. Оценщик ёмкости: `avtobus capacity plan`
Ввод: rate, размер, latency хендлера → вывод: воркеры/партиции/prefetch/реплики и прогноз лага (модель M/M/c, честные формулы в доках).

### 386. Бэкофф чтения пустых очередей
Adaptive polling для SQL/Redis транспортов: 0 сообщений → интервал растёт до потолка, NOTIFY/новое сообщение сбрасывает (экономия БД в тишине).

### 387. Дешёвые таймеры: колесо времени (timing wheel)
Миллионы отложенных in-memory событий (debounce, деферы) — hashed timing wheel вместо кучи Task.Delay.

### 388. Согласованное хэширование партиций
Jump consistent hash для ключ→партиция — минимальная перетасовка при смене числа партиций.

### 389. Zero-alloc метрики
`Meter` API с tag-кэшированием (bounded cardinality), никаких string.Format на горячем пути.

### 390. Бенч «дуэль транспортов»
`avtobus bench --transports inmemory,rabbit,kafka --payload 1kb --pattern fanout` — сравнение на вашем железе, а не в маркетинге.

### 391. Реактивная пауза БД-давления
Пул БД насыщен (wait time растёт) → шина сама сбрасывает prefetch/parallelism (сигнал от EF Core interceptor-а) — БД не умирает первой.

### 392. Компакция In-Memory транспорта
Debounce/snapshot-семантика (идеи 30/145) в InMemory — старые сообщения ключа заменяются, память ограничена при burst-ах.

### 393. Формат заголовков: бинарный short-code реестр
Частые заголовки кодируются байтом (реестр в спеке транспорта) — экономия 50–100 байт на сообщение в масштабе миллиардов — заметные деньги.

### 394. Специализация JSON для конвертов
Envelope сериализуется рукописным writer-ом (не общий STJ путь) — конверт дешевле тела.

### 395. NUMA/Container-aware дефолты
Параллелизм по `Environment.ProcessorCount` с учётом cgroup limits (.NET 10 честно отдаёт); пороги буферов от доступной памяти контейнера.

### 396. Тесты производительности деградации
Сценарий «брокер медленный/флапает» в бенч-сьюте: throughput деградирует линейно, не обрывом; память ограничена (bounded everything).

### 397. Кванты работы и справедливость
Один консьюмер не может занять все воркеры процесса: weighted fair scheduling между консьюмерами (вдохновение: Linux CFS, упрощённо).

### 398. Скоростной путь идемпотентности
Bloom (идея 158) + LRU положительных попаданий в памяти → 99% дублей отсекаются без БД.

### 399. Пассивные реплики консьюмеров (hot standby)
Реплика подключена, но не потребляет (single-active); failover < 1с без ребаланса — для строгих очередей команд.

### 400. Бюджет холодного старта
Гейт CI: время от `Program.Main` до первого обработанного сообщения ≤ 500 мс (JIT) / ≤ 100 мс (AOT) на эталонном примере — DX и serverless.
